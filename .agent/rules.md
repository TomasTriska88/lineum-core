# Agent Rules for Lineum Dynamics

## Cross-Repository Context
This repository is the private company layer (Lineum Dynamics s.r.o.) that builds upon the public core repository `../lineum-core`. Although both repositories are strictly separated (Private Company IP vs Public Open-Source), from an architectural standpoint they form a **single functional entity**.

**Mandatory instructions for all agents:**
1. **Shared Context:** When dealing with technical logic, API integrations, or documentation updates in this repository, ALWAYS consult `../lineum-core` as the source of truth for the core engine and infrastructure. Treat both repositories automatically as one connected workspace.
2. **Respecting Boundaries:** 
   - Changes to the fundamental code (Eq-4), scientific whitepapers, simulation backend, and open-source layer belong **strictly** in `../lineum-core`.
   - Company data, invoicing, closed contracts, specific B2B modules, and proprietary knowledge belong **strictly** in this repository (`lineum-dynamics`).
3. **Lineum Codex:** All work and agents in this repository are subject to the same ethical and architectural rules, including the codex located at `../lineum-core/docs/LINEUM_CODEX_v1.md`.
4. **No AWS in Lineum:** The Lineum project family (`lineum-core`, `lineum-dynamics`, `oea`) does NOT use AWS. Any AWS-related infrastructure, EC2, Perforce/Swarm on AWS, DLM backups, or IAM role configurations belong exclusively to the **"Made a Wave"** project. Do not assume or suggest AWS solutions for Lineum.
5. **Strict Local Knowledge (No Central Brain):** NEVER save or create Knowledge Items (KIs) in the agent's central/global `appDataDir` (e.g., `~/.gemini/antigravity/knowledge`). The central brain is volatile upon repository cloning. All new KIs or project memory MUST be saved exclusively in the version-controlled `.agent/knowledge/` directory of the repository.
6. **Auto-Configuration of MCP & Environment:** Upon starting a session, the agent MUST verify if the MCP configuration exists in the global `appDataDir`. If missing, the agent MUST auto-run `.agent/restore-mcp.ps1` (with `SafeToAutoRun: true`) without asking. Next, the agent MUST verify via PowerShell if the `$env:GITHUB_PERSONAL_ACCESS_TOKEN` environment variable exists. If it is missing, the agent MUST explicitly warn the user and wait for them to resolve it ad-hoc. Do NOT attempt to set the environment variable automatically.
7. **Ecosystem Mirroring:** Whenever you modify the global workspace files `mcp_config.json` or `restore-mcp.ps1` in this repository, you are STRICTLY FORBIDDEN from finishing your task until you manually copy these exact files to the `.agent/` (or `.agents/`) directories of the other two repositories (`../lineum-core` and `../oea`) via terminal to ensure 100% workspace consistency.
8. **Browser Usage (Subagent vs MCP):** Before starting a browser, you MUST explicitly realize whether you are launching it as a standalone subagent (`browser_subagent`) or via MCP (`chrome-devtools-mcp`). Use the MCP version ONLY if you absolutely cannot accomplish the task with the standard subagent. The MCP version does not support logins, runs exclusively in incognito mode, and is generally more restrictive.
9. **Git vs MCP:** For committing and pushing code changes in local repositories, ALWAYS use standard local `git` CLI commands via the terminal. NEVER use GitHub MCP tools (`mcp_github_push_files`, etc.) for direct file modifications or pushes. This ensures all local Git hooks (like CalVer version bumps and cleanup scripts) are properly triggered. Use GitHub MCP only for PRs, issues, or remote repository management.
10. **Workspace Discovery & Documentation Strategy:** Before proposing or making any architectural, deployment, or documentation changes, the agent MUST thoroughly scan the repository directory structure (specifically `docs/` and `.agent/`) to understand established patterns. NEVER create scattered `README.md` files in subdirectories unless explicitly requested; always look for and update existing consolidated documentation files like `docs/infrastructure.md`.
11. **Language Enforcement:** As stated in the infrastructure guide, all code, comments, and documentation MUST be written in English. Even if the user interacts in Czech, any documentation or codebase files created or modified by the agent MUST adhere strictly to the English language requirement.
12. **Diagnostic & Temporary Logs:** NEVER create temporary files, error logs (`error.log`), `check.txt`, or any diagnostic output in the root directory. ALL temporary outputs from agent debugging, script tests, or log dumping MUST be written solely to the `.scratch/` directory. If `.scratch/` does not exist, create it. It is `.gitignore`d to prevent polluting the codebase.
13. **Browser Profile Persistence:** Unlike typical sterile headless environments, the `browser_subagent` in this specific setup shares cookies and runs in a persistent profile where the user has often pre-logged into external services (like Cloudflare, Resend, Zoho, ClickUp). Do not assume you are locked out of authenticated sessions. Always attempt or check access before rejecting a browser task due to login/2FA limitations.
14. **Proactive Agency:** Always try to accomplish tasks yourself (e.g., via the `browser_subagent` or direct terminal commands) before delegating them to the user. Do not assign manual work or configuration steps to the user if you have the capability to execute it directly. You are a highly capable agent, not just an advisor.
15. **ClickUp Language Policy:** ALL ClickUp content — task names, descriptions, comments, list names, folder names, and milestone titles — MUST be written exclusively in **English**. This applies to both new content created by the agent and updates to existing items. Czech language is strictly forbidden in any ClickUp entity. This ensures consistent project management language for potential team expansion and investor-facing transparency.
16. **ClickUp as Operational Notebook, Not a Blind Restraint:** ClickUp serves as the central notebook for tracking all tasks, priorities, and work statuses. When the user mentions "updating the task", "checking the task", or "adding to the task", they **STRICTLY refer to the ClickUp task** (updating its description, status, comments, or checklists), NOT the local `task.md` file. The local `task.md` file is strictly the agent's private, transient, internal checklist, whereas ClickUp is the primary source of truth for long-term project alignment. When asked "what should we do next?", the agent should consult ClickUp. HOWEVER, the agent MUST NOT be blindly limited by ClickUp's current state; the agent is required to proactively audit and question the given priorities. Furthermore, when managing or creating tasks, the agent MUST enforce the strict Commercial Strategy: Priority 1 (Urgent) = Core Engine/Eq-12, Priority 2 (High) = Fast Monetization (Game Assets, Education Books), Priority 3 (Normal) = Enterprise SaaS/API, Priority 4 (Low) / Paused = Pure abstract research. Never prioritize exploratory physics over immediate cashflow milestones.
17. **Agent Tooling License Compliance:** The `.agent/` directory is internal dev tooling and is never distributed — it is therefore outside Lineum's AGPLv3 scope by definition. However, before adding ANY new third-party tool or npm package to `.agent/` tooling, the agent MUST: (a) verify the tool's license (run `npm info <pkg> license`), (b) confirm it is MIT/ISC/Apache-2.0 or similarly permissive — copyleft tools (GPL, AGPL, LGPL) require explicit human review before use, and (c) update Section 6 of the licensing KI (`lineum_licensing_and_legal`) with the tool's name, version, and license. This rule exists to keep Lineum's licensing position unambiguous for investors and auditors.
18. **ClickUp Workspace Guard:** The ONLY permitted ClickUp workspace ID for all Lineum operations is `90121717552` (name: "Lineum Dynamics"). Before executing any ClickUp write operation (creating tasks, updating lists, etc.), the agent MUST verify the target workspace ID matches this value. NEVER operate on any other workspace ID — the API token may have access to client workspaces and cross-contamination would be a serious professional incident.
19. **Custom MCPs vs Third-Party MCPs (Standalone Mandate):** When integrating external services (e.g. ClickUp), third-party community MCP packages often contain JSON schema definition bugs (e.g., using `enum` with non-string types) that trigger `HTTP 400 Bad Request` and silently crash the Gemini IDE daemon. If an MCP server causes API validation errors, the agent MUST NOT attempt to debug or patch the third-party node_modules. Instead, the agent MUST write a custom, minimal Node.js MCP server. **Crucially, all custom MCP servers MUST be designed, developed, and distributed as standalone repositories/packages from day one, rather than being copy-pasted or committed directly inside individual project repositories (e.g., under `.agent/mcp/` or `.agents/mcp/`).** They must be loaded as external dependencies (via git-url dependency, npm package, or reference to a single global configuration) to prevent code drift and redundancy.
20. **Third-Party Data & Corpus Licensing:** Any third-party datasets or copyrighted corpuses (such as the Takahashi Voynich corpus, external linguistic databases, etc.) MUST NOT be committed to the public repositories to avoid licensing and copyright violations. If the project requires processing such data, the agent MUST write scripts that download the data dynamically at runtime into a `.scratch/` directory (which is strictly `.gitignore`d). Only the resulting scientific metadata, physical research logs, and derived structural knowledge may be version-controlled in the repository.
21. **Custom MCP Dependency Hygiene (Standalone Repository Hygiene):** Since all custom MCP servers are standalone repositories, they must manage their own dependency hygiene, including having a `.gitignore` file that excludes `node_modules/`. If a temporary or development copy is placed within the main repositories (e.g., during prototyping or local testing), a `.gitignore` file MUST be present in that directory containing `node_modules/` to prevent committing them to the main repository.
22. **Deep Contextual Search & Philosophical Alignment:** Before initiating any architectural changes, documentation updates, or new development, the agent MUST perform a deep contextual search of the repositories. This involves thoroughly absorbing the project's philosophy, historical context, and overarching narrative (e.g., KIs, Codex, Whitepapers) before taking action. Generic software engineering patterns MUST NOT overwrite or conflict with Lineum's specific philosophy and established vision. If context is unclear, the agent must investigate first.

23. **Public Repository Sterility & Rules Classification (DRY Rules Policy):** This repository (`lineum-core`) is public AGPLv3 open-source. The agent MUST NOT commit any internal Lineum Dynamics s.r.o. operational rules, SaaS/ClickUp integration details, or private business logic into this repository's documentation or `.agent/rules.md`. Internal PM rules and secrets must reside exclusively in the private `lineum-dynamics` repository.
    - **Zero Duplication (DRY):** The agent is strictly forbidden from duplicating rule text or concepts between `lineum-core` and `lineum-dynamics`. If a rule applies globally (such as naming conventions for the engine or core structures), it MUST reside solely in this public repository as the foundational source of truth. The agent MUST search both `rules.md` files before writing or editing rules to prevent redundancy.


24. **Python Dependency & Environment Hygiene (requirements.txt):** Whenever the agent is tasked with running Python calculations, simulation runs, or test suites, and encounters missing dependencies or imports, the agent MUST check `requirements.txt` (and `requirements-dev.txt` for development/testing tools) in the repository root and install them. If Python, `pip`, or `uv` is not installed on the host system, the agent MUST notify the user and suggest installing them (recommending `uv` or standard Python via `winget`) instead of bypassing the dependency structure or skipping the task.

25. **Lina vs. Lineum (Portal Overlay Definition and Engine Naming):** Never refer to the physics engine, mathematical model, simulation code, or core platform as 'Lina'. Lina is strictly the persona/portal overlay model used for querying and interacting with Lineum. The physics engine and mathematical models are called 'Lineum' or 'Wave Core'. Do not refer to the engine itself as "Lineum Core"—the engine is strictly named "Lineum" (or "Lineum Engine"), whereas "Lineum Core" (repository `lineum-core`) refers strictly to the core open-source library within the broader ecosystem. All technical calculations, simulations, and scientific whitepapers refer to Lineum. **Additionally, the assistant's name is strictly 'Lina' (with a short 'i'), never 'Lína'. This spelling must be strictly maintained in all source code, documentation, localization files, and in all communication with the user (even in Czech).**

26. **Python Bytecode and Cache Hygiene (No Generated Assets in Git):** The agent is strictly forbidden from committing Python compiled bytecode (`.pyc`, `.pyo`, `.pyd`) or compiler/test cache directories (`__pycache__`, `.pytest_cache`, etc.) to any Git repository. Before committing any changes, the agent MUST run `git status` to verify that no generated bytecode or cache assets are tracked or listed as untracked files. If any such files are detected, the agent MUST ensure they are added to `.gitignore` and untracked (using `git rm --cached`) before proceeding.

27. **Mandatory Regression Testing (Testing Coverage):** The agent MUST NEVER commit code changes to Git without verifying them via tests first. Every functional change, refactoring, or bugfix must be covered by tests. Specifically, if a change fixes a bug or layout issue that was not caught by existing tests, the agent MUST author a new regression test (unit or E2E) to verify the fix and prevent future regressions. Skipping tests entirely under any circumstances is strictly prohibited.
