# Agent Rules for Lineum Core

## Cross-Repository Context

This repository (`lineum-core`) is the public, open-source layer containing the core physics engine (Eq-4), simulation backend, and scientific whitepapers. It is developed alongside the private company layer `../lineum-dynamics` and the visual assets repository `../oea`.

**Mandatory instructions for all agents:**

1. **Shared Context:** When dealing with technical logic, physics formulas, or simulation parameters, always treat the three repositories as a connected workspace.
2. **Respecting Boundaries:**
   - Changes to the fundamental code (Eq-4), scientific whitepapers, simulation backend, and open-source layer belong **strictly** in this repository (`lineum-core`).
   - Company operational data, Zoho email setups, ClickUp workflows, invoicing, and B2B commercial modules belong **strictly** in `lineum-dynamics`.
3. **Lineum Codex:** All work in this repository is subject to the ethical and architectural rules of the Lineum Codex located at `docs/LINEUM_CODEX_v1.md`.
4. **No AWS in Lineum:** The Lineum project family does NOT use AWS. Any AWS-related infrastructure belongs exclusively to the "Made a Wave" project. Do not assume or suggest AWS solutions for Lineum.
5. **Strict Local Knowledge (No Central Brain):** NEVER save or create Knowledge Items (KIs) in the agent's central/global `appDataDir`. All new KIs or project memory MUST be saved exclusively in the version-controlled `.agent/knowledge/` directory.
6. **Auto-Configuration of Git Hooks:** The agent MUST verify and set `git config core.hooksPath .agent/hooks` at the very start of any session to guarantee that Git pre-commit hooks are active in the local repository.
7. **Ecosystem Mirroring:** Whenever you modify the global workspace files `mcp_config.json` or `restore-mcp.ps1` in this repository, you MUST copy these exact files to the `.agent/` (or `.agents/`) directories of the other two repositories (`../lineum-dynamics` and `../oea`) via terminal to ensure 100% workspace consistency.
8. **Browser Usage (Zero-Browser Feasibility Check):** Before launching the browser subagent under any circumstances, the agent MUST explicitly ask itself: "Can this task be accomplished without a browser (e.g., via terminal commands, local file modifications, or custom MCP tool extensions)?" If yes, the agent is strictly forbidden from launching the browser subagent.
9. **Git vs MCP:** For committing and pushing code changes in local repositories, ALWAYS use standard local `git` CLI commands via the terminal. NEVER use GitHub MCP tools for direct file modifications or pushes.
10. **Workspace Discovery & Document Locality (Source File Isolation):** Before proposing or making any architectural changes, thoroughly scan the repository structure (specifically `docs/` and `.agent/`). Never modify files inside `portal/src/lib/data/` directly if they are target paths in `portal/scripts/sync-data.js`. The agent MUST only edit their respective source files in `.agent/rules.md`, `.agent/workflows/`, `docs/`, `whitepapers/`, etc., and then run `node scripts/sync-data.js` (or `npm run sync`) from the `portal` directory to compile and update the targets.
11. **Language Enforcement:** All code, comments, and documentation MUST be written in English. Even if the user interacts in Czech, any documentation or codebase files created or modified by the agent MUST adhere strictly to the English language requirement.
12. **Diagnostic & Temporary Logs:** NEVER create temporary files, error logs (`error.log`), `check.txt`, or any diagnostic output in the root directory. ALL temporary outputs from agent debugging or script tests MUST be written solely to the `.scratch/` directory.
13. **Browser Profile Persistence:** Sharing persistent profile cookies is allowed if browser-subagent read-only actions are required.
14. **Proactive Agency:** Always try to accomplish tasks yourself (using direct terminal commands or highly restricted browser subagent runs) before delegating them to the user.
15. **Agent Tooling License Compliance:** Before adding any new third-party tool or npm package to `.agent/` dev tooling, verify the tool's license (MIT/ISC/Apache-2.0 permissive) and log it in the licensing KI.
16. **Python Dependency & Environment Hygiene (requirements.txt):** When running Python calculations, simulation runs, or test suites, check `requirements.txt` (and `requirements-dev.txt`) in the repository root and install them.
17. **Lina vs. Lineum (Portal Overlay Definition and Engine Naming):** Never refer to the physics engine, mathematical model, simulation code, or core platform as 'Lina'. Lina is strictly the persona/portal overlay model used for querying and interacting with Lineum. The physics engine is named "Lineum" (or "Lineum Engine"), whereas "Lineum Core" refers strictly to the core open-source library. The assistant's name is strictly 'Lina' (with a short 'i'), never 'Lína'.
18. **Python Bytecode and Cache Hygiene (No Generated Assets in Git):** The agent is strictly forbidden from committing Python compiled bytecode (`.pyc`, `.pyo`, `.pyd`) or compiler/test cache directories (`__pycache__`, `.pytest_cache`). Run `git status` to verify before committing.
19. **Mandatory Regression Testing (Testing Coverage):** The agent MUST NEVER commit code changes to Git without verifying them via tests first. Every functional change, refactoring, or bugfix must be covered by tests. If a change fixes a bug or layout issue not caught by tests, author a new regression test (unit or E2E). When creating a new UI component, shared utility, or API module, write a dedicated unit test suite for it before committing.
20. **Component Modularity & Design Sync (Anti-Duplication Guard):** Before refactoring UI layouts, forms, buttons, or states, review existing components in `$lib/components/` and `DESIGN_GUIDE.md`. Extract layout patterns used in 2 or more places into reusable Svelte components and document them in `portal/docs/DESIGN_GUIDE.md` under Section 6.
21. **Global Project Strategic Pipeline (The Engine-First Rule):** Evaluate the repository's current state against this pipeline and find the lowest uncompleted tier:
    - **Phase 1: The Source of Truth** - Core Physics Engine: Implement/update the fundamental mathematical PDE solver (absolute baseline).
    - **Phase 2: Commercial & Empirical Proofs** - Commercial API & Products, Lab Verifications (E2E numerical tests to protect new engine features).
    - **Phase 3: Project Hygiene & Documentation** - Whitepaper Integration (extract conceptual notes and integrate into whitepapers when tests pass), Web Platform & Marketing.
22. **Knowledge Base Restoration:** Upon cloning, if the local agent KI store is empty, automatically execute `.agent/restore-knowledge.ps1` without asking for permission (SafeToAutoRun).
23. **Simulacrum vs. Portal Boundaries and Scientific Integrity:** Never mix up Simulacrum and Portal. Simulacrum is strictly the physics laboratory and research environment for verified, audited claims. Portal is the premium presentation and marketing layer for visitors. Never present unproven or unaudited theoretical hypotheses (such as standard model particles like Protons, Neutrons, or Electrons mapped to Lineum fields) as verified physical facts on the Portal. Any physical analogies shown on the public Portal must be presented strictly as conceptual lore or artistic illustrations, keeping scientific claims gated inside the audited laboratory.
24. **Static Verification and Runtime Smoke Checks:** To prevent compilation errors, missing dependency imports, or silent runtime failures:
    - **Refactoring & File Moves:** Whenever any folder layout, component path, directory structure, or file location is changed or refactored, the agent MUST immediately execute static compilation checks (e.g. `npm run check` or `svelte-check` for the Portal) and run all unit tests.
    - **Component Compilation Tests:** When creating or moving Svelte components or key UI modules, add or update a unit test that explicitly imports the component. This forces the test compiler (e.g. Vitest) to resolve and compile the component, catching import issues immediately.
    - **Runtime Console Verification:** Before declaring a frontend task complete, run the dev server locally and use the browser subagent (or direct automated page load) to visit the main page. Verify that the page loads correctly and inspect the console logs to ensure there are zero runtime exceptions, errors, or failed import logs.
25. **Mandatory Lay-First, Layered User Communication:** Treat the project owner primarily as a software developer and system architect who is learning the mathematical and scientific concepts while the research progresses. All project-owner chat updates, questions, progress reports, negative results, decisions, and final summaries must be understandable without specialist training. Start with the plain answer in one or two sentences, then give a concrete mental picture, analogy, small example, or everyday-scale comparison, and then state what the result practically changes for Lineum. Never lead with equations, raw scientific labels, implementation identifiers, statistical jargon, long metric tables, or unexplained powers of ten. Translate every important magnitude into an intuitive comparison and define every unavoidable scientific term on first use. When technical precision is needed, layer the answer in this order: (1) the concise lay conclusion, (2) a visual or everyday explanation, (3) the consequence for Lineum or the current decision, and only then (4) the exact mathematics, assumptions, units, code details, evidence level, and remaining uncertainty. Keep the technical layer available for audit, but do not force the owner to decode it to understand the outcome. Clearly distinguish “the code does this,” “the simulation observed this,” “we interpret this,” and “we hypothesize this.” Increase technical depth only when the project owner explicitly requests it or when exact detail is necessary for a consequential decision, while still retaining the lay opening.
26. **Small-Step Development and Negative-Result Owner Gate:** Advance scientific, mathematical, and architectural development through small, reversible, independently verifiable steps. Before moving to the next consequential step, explain in plain language what changed, why it changed, what evidence was produced, what remains uncertain, and what decision follows. Do not continue past a material conceptual or architectural decision while the project owner indicates that they do not yet fully understand it. Do not interrupt normal research with speculative preference questions, optional side questions, requests for intuition, ordinary uncertainty, or the mere existence of multiple viable paths. Resolve those situations autonomously through preregistered decision rules, the cheapest safe calculation, a reversible experiment, or the most conservative evidence-preserving path. In Lineum research, ask the project owner for a lay, common-sense, creative, or out-of-the-box perspective only after a verified negative result: for example, a failed control, a falsified hypothesis, a material contradiction, or evidence that the intended mechanism does not work under the declared test. Do not treat an untested suspicion, preliminary warning, implementation inconvenience, or merely incomplete evidence as a negative result. At the negative-result gate, stop blind parameter tuning and local optimization; present the smallest useful evidence set in plain language, explain what failed and why it matters, and explicitly ask for the project owner's intuitive and out-of-the-box interpretation before selecting a replacement mechanism. Asking the project owner any question is a hard stop for the active goal: after emitting the question, perform no further research, diagnostics, edits, tests, simulations, external actions, or supposedly safe side work until the owner answers. A question must therefore appear only in the final response of the turn, never as a non-blocking aside while work continues. Questions that are independently required for safety, authorization, or access remain blocking, but they must not be disguised as scientific intuition requests.
27. **Permanent Research History:** Keep every completed or decision-relevant research report under `research/` in version control even after its conclusions are integrated into code or whitepapers. A research report is the durable historical record of the questions, evidence, calculations, simulations, negative results, rejected paths, uncertainty, and decision rationale. Integration, disagreement, or later supersession does not authorize silent rewriting or deletion of that history. Delete a published research record only with explicit project-owner approval and a documented reason.
28. **Research Naming, Status, and Versioning:** Name research reports by their scientific subject, never by their language or a vague sequence such as `research-2` or `final-new`. Every report must state its status (`draft`, `active`, `validated`, or `superseded`), semantic or dated version, evidence cutoff date, scope, central questions, and current confidence level. Before a report informs code or canonical claims, give it a stable descriptive filename. When later evidence materially changes a decision-relevant report, preserve the prior Git history, increment the report version or create a clearly related successor, and state which conclusions were superseded and why.
29. **Standalone, Portable, and Reproducible Research:** Every permanent research report must remain complete, understandable, auditable, and operational when copied out of the repository as a single document. Include all questions, definitions, equations, assumptions, units, parameter values, input data needed for the reported calculations, algorithms or pseudocode, executable verification code, machine-readable outputs, human-readable results, uncertainty, failure conditions, limitations, and reproduction instructions required to reproduce or challenge every material conclusion. Never use “see another document,” a repository path, a temporary artifact, hidden notebook state, uncommitted output, or an unpublished dataset as a substitute for essential content. A report may cite external scholarly sources for attribution and source provenance, and must provide complete portable citations such as a title, author, year, DOI, or stable URL; however, its own reasoning, methods, and reported computations must not depend on access to another Lineum document or repository file. If earlier Lineum research is relevant, restate all decision-relevant premises and evidence rather than requiring the reader to retrieve it.
30. **Temporary Experiment Boundary:** Store exploratory scripts, translation drafts, caches, intermediate data, diagnostic logs, and disposable simulation outputs only under `.scratch/`. Do not cite `.scratch/` artifacts as permanent evidence. Promote a result into `research/` only after its important inputs, method, outputs, and limitations have been captured in the self-contained report. Keep intentionally permanent raw datasets or reusable verification tools only when they have a clear research purpose, stable naming, provenance, and documentation.
31. **Research, Code, and Whitepaper Canon Separation:** Treat the three layers as complementary rather than interchangeable: research records why a conclusion was considered credible at a point in time; code defines the current implemented behavior; whitepapers define the current canonical scientific claims. A research conclusion does not become a verified Lineum claim merely because it appears in `research/`. Promote it into code or whitepapers only through a small, explicit, independently tested step that records the supporting evidence, known limitations, and remaining falsification tests. If implementation or canonical text diverges from earlier research, mark the research conclusion as superseded or unresolved instead of retroactively presenting it as confirmed.
32. **Discovery-First Creativity and Evidence-Strict Validation:** Separate scientific work into an explicitly generative phase and an explicitly adversarial validation phase. During generation, do not reject a hypothesis merely because it is unconventional, crosses disciplinary boundaries, or conflicts with a currently dominant model; ask what additional mechanism, regime, variable, scale, or observable would make it coherent and what established evidence it would still need to reproduce. During validation, grant no exception for novelty, intuition, elegance, or project preference. A conflict with current theory is a research question rather than an automatic veto, but a viable replacement must explain the successful evidence of the theory it seeks to replace and produce a discriminating prediction. Novelty is neither evidence against nor evidence for a claim.
33. **Failure-to-Mechanism Protocol:** Treat every decision-relevant negative result as a map of missing mechanisms, not as automatic deletion of the broad research direction. Before abandoning, retuning, or replacing a hypothesis, record: (a) exactly what failed and within which declared scope; (b) what behavior remained positive or unexplained; (c) whether the failure belongs to the equation, parameter regime, initial state, observer, resolution, boundary, calibration, or interpretation; (d) what necessary or sufficient ingredient would have to differ for success; (e) at least three qualitatively distinct repair classes when scientifically plausible; and (f) the cheapest frozen test that separates those repairs. Distinguish “this implementation is falsified,” “this regime is unsupported,” “the observer is non-identifying,” “a mechanism is missing,” and “the broader hypothesis is falsified”; use the last status only when the experiment had power over the broader claim. Preserve all failed protocols and do not hide them through threshold tuning.
34. **Mechanism Synthesis Without Unconstrained Hybrids:** Actively look for non-obvious bridges among topology, solitons, gauge fields, nonequilibrium structures, stochastic resonance, memory, dynamic media, information thermodynamics, causal geometry, quantum composition, and other relevant domains. For every proposed bridge, state the shared mathematical structure, units or dimensionless variables, causal mechanism, known incompatibilities, and a counterfactual test that could reject the connection. Add candidate mechanisms one at a time or through a factorial ablation; do not combine every attractive idea into an unfalsifiable model that can fit any finite output.
35. **Owner Out-of-the-Box and Common-Sense Failure Gate:** Apply this gate only after the verified negative-result conditions in Rule 26 are satisfied, never from a preliminary suspicion or merely incomplete evidence. Before choosing the next consequential equation, mechanism, or architecture, explain the negative result to the project owner in plain language, including what still works, why the result is surprising, and what would have to change. Explicitly ask for the owner's intuitive, common-sense, architectural, and out-of-the-box ideas, then hard-stop the active goal as required by Rule 26. After the owner responds, translate each resulting idea into equations, assumptions, simulations, controls, and falsification criteria; compare it fairly with internally generated alternatives. Owner intuition is a required source of candidate hypotheses at this gate, not automatic evidence that a candidate is true.
36. **Exhaustive Variant Coverage and Reopenable Rejection Ledger:** At every material fork in an equation, mechanism, boundary law, initial condition, scale, observer, interpretation, or architecture, identify and register every currently known, scientifically distinguishable, and testable variant. Include the current implementation, the documented formulation, conventional alternatives, null controls, symmetry-preserving and symmetry-breaking cases, mixed mechanisms, project-owner ideas, and credible cross-disciplinary or out-of-the-box candidates. Never exclude a registered variant because it is unconventional, conflicts with the current whitepaper or dominant theory, appears aesthetically inelegant, or failed a different test. Because the logically possible variant space is unbounded, “exhaustive” means maintaining an explicit open registry and coverage matrix for every variant that has actually been identified, recording newly discovered variants immediately, and stating which families remain unexplored; it does not permit pretending that all imaginable equations have been enumerated. Prioritize variants with discriminating calculations, controls, and factorial ablations rather than silently discarding inconvenient branches. Excluding or downgrading a variant requires evidence with power over the exact claim and a recorded validity audit of the equation, parameters, units, initial state, boundary, resolution, observer, horizon, statistics, and falsification condition. Use scope-safe statuses such as `untested`, `queued`, `active`, `supported`, `unsupported_under_tested_conditions`, `falsified_within_domain`, `dormant`, `superseded`, and `reopened`; never turn a bounded negative result into “impossible everywhere.” Never delete or overwrite an excluded, dormant, or superseded variant. Preserve its exact formulation, provenance, rationale, complete test conditions, raw result, reason for status, unresolved alternative explanations, and explicit reopen triggers in the permanent standalone research record. If later evidence shows that the original test, observer, calibration, or scope was inadequate, mark that evidence and reopen the variant without rewriting its history.
37. **Mandatory Existing-Hypothesis Retrieval Before Mechanism Synthesis:** Whenever a verified negative result opens the owner out-of-the-box gate, the project owner proposes a creative explanation, or research is about to select a replacement mechanism, first perform a thorough retrieval of all already recorded Lineum ideas that could bear on the problem. Search the relevant code, research history, whitepapers, hypotheses, experiments, visual or mathematical models, and project knowledge across `lineum-core`, `lineum-dynamics`, `oea`, and `lina-ei`, plus the relevant external task system when it may contain decision history. Do this automatically before asking the owner to remember prior ideas and before inventing a supposedly new mechanism. Treat retrieved material as hypothesis provenance, not as validation: identify contradictory versions, deprecated fields or equations, missing evidence, circular observers, and claims that outrun their recorded tests. Translate every scientifically distinguishable retrieved idea into the reopenable variant ledger with an explicit equation or causal graph, assumptions, conserved or exchanged quantities, controls, falsification criteria, cheapest discriminating test, and relationship to current implementation. Compare retrieved candidates fairly with owner ideas, conventional mechanisms, null controls, and newly generated out-of-the-box alternatives. Do not merge historically different ideas into one unfalsifiable narrative merely because they share a metaphor such as a fountain, reservoir, memory, horizon, or higher layer.
38. **Mandatory Three-Layer Universe Comparison:** For every decision-relevant Lineum mechanism, equation, simulation result, interpretation, proposed repair, and candidate public claim, explicitly evaluate and keep separate three evidence layers: (1) what the current Lineum implementation actually computes, including its equations, boundary conditions, parameters, numerical limits, and reproducible observations; (2) what the best available current empirical evidence and established or actively contested physical models say about our observable universe, using current primary or authoritative sources and stating observational bounds, model dependence, unresolved tensions, and the evidence cutoff date; and (3) what remains a Lineum hypothesis, analogy, extrapolation, or speculative extension beyond current evidence. Never use agreement inside the implementation as evidence that nature behaves the same way, never treat the absence of a standard mechanism as disproof of an unconventional candidate, and never present a speculative bridge as established cosmology. For each material comparison, state the shared observable or mathematical structure, the important mismatch, the cheapest discriminating test, and what result would support, constrain, or falsify the exact claim within the tested domain. Refresh time-sensitive external evidence before a report, code decision, whitepaper update, or public communication relies on it, and preserve both supporting and conflicting observations in the standalone research record.
