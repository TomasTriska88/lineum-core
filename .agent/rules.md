# Agent Rules for Lineum Core

## Cross-Repository Context

This repository (`lineum-core`) is the public, open-source layer containing the core physics engine (Eq-4), simulation backend, and scientific whitepapers. It is developed alongside the private company layer `../lineum-dynamics` and the visual assets repository `../oea`.

**Mandatory instructions for all agents:**

1. **Shared Context:** When dealing with technical logic, physics formulas, or simulation parameters, always treat the three repositories as a connected workspace.
2. **Respecting Boundaries:**
   - Changes to the fundamental code (Eq-4), scientific whitepapers, simulation backend, and open-source layer belong **strictly** in this repository (`lineum-core`).
   - Company operational data, Zoho email setups, ClickUp workflows, invoicing, and B2B commercial modules belong **strictly** in `lineum-dynamics`.
3. **Lineum Codex:** All work in this repository is subject to the ethical and architectural rules of the Lineum Codex located at `docs/LINEUM_CODEX_v1.md`.
4. **No AWS in Lineum:** The Lineum project family does NOT use AWS. Any AWS-related infrastructure belongs exclusively to the "Made a Wave" project. Do not assume or suggest AWS solutions for Lineum.
5. **Strict Local Knowledge (No Central Brain):** NEVER save or create Knowledge Items (KIs) in the agent's central/global `appDataDir`. All new KIs or project memory MUST be saved exclusively in the version-controlled `.agent/knowledge/` directory.
6. **Auto-Configuration of Git Hooks:** The agent MUST verify and set `git config core.hooksPath .agent/hooks` at the very start of any session to guarantee that Git pre-commit hooks are active in the local repository.
7. **Ecosystem Mirroring:** Whenever you modify the global workspace files `mcp_config.json` or `restore-mcp.ps1` in this repository, you MUST copy these exact files to the `.agent/` (or `.agents/`) directories of the other two repositories (`../lineum-dynamics` and `../oea`) via terminal to ensure 100% workspace consistency.
8. **Browser Usage (Zero-Browser Feasibility Check):** Before launching the browser subagent under any circumstances, the agent MUST explicitly ask itself: "Can this task be accomplished without a browser (e.g., via terminal commands, local file modifications, or custom MCP tool extensions)?" If yes, the agent is strictly forbidden from launching the browser subagent.
9. **Git vs MCP:** For committing and pushing code changes in local repositories, ALWAYS use standard local `git` CLI commands via the terminal. NEVER use GitHub MCP tools for direct file modifications or pushes.
10. **Workspace Discovery & Document Locality (Source File Isolation):** Before proposing or making any architectural changes, thoroughly scan the repository structure (specifically `docs/` and `.agent/`). Never modify files inside `portal/src/lib/data/` directly if they are target paths in `portal/scripts/sync-data.js`. The agent MUST only edit their respective source files in `.agent/rules.md`, `.agent/workflows/`, `docs/`, `whitepapers/`, etc., and then run `node scripts/sync-data.js` (or `npm run sync`) from the `portal` directory to compile and update the targets.
11. **Language Enforcement:** All code, comments, and documentation MUST be written in English. Even if the user interacts in Czech, any documentation or codebase files created or modified by the agent MUST adhere strictly to the English language requirement.
12. **Diagnostic & Temporary Logs:** NEVER create temporary files, error logs (`error.log`), `check.txt`, or any diagnostic output in the root directory. ALL temporary outputs from agent debugging or script tests MUST be written solely to the `.scratch/` directory.
13. **Browser Profile Persistence:** Sharing persistent profile cookies is allowed if browser-subagent read-only actions are required.
14. **Proactive Agency:** Always try to accomplish tasks yourself (using direct terminal commands or highly restricted browser subagent runs) before delegating them to the user.
15. **Agent Tooling License Compliance:** Before adding any new third-party tool or npm package to `.agent/` dev tooling, verify the tool's license (MIT/ISC/Apache-2.0 permissive) and log it in the licensing KI.
16. **Python Dependency & Environment Hygiene (requirements.txt):** When running Python calculations, simulation runs, or test suites, check `requirements.txt` (and `requirements-dev.txt`) in the repository root and install them.
17. **Lina vs. Lineum (Portal Overlay Definition and Engine Naming):** Never refer to the physics engine, mathematical model, simulation code, or core platform as 'Lina'. Lina is strictly the persona/portal overlay model used for querying and interacting with Lineum. The physics engine is named "Lineum" (or "Lineum Engine"), whereas "Lineum Core" refers strictly to the core open-source library. The assistant's name is strictly 'Lina' (with a short 'i'), never 'Lína'.
18. **Python Bytecode and Cache Hygiene (No Generated Assets in Git):** The agent is strictly forbidden from committing Python compiled bytecode (`.pyc`, `.pyo`, `.pyd`) or compiler/test cache directories (`__pycache__`, `.pytest_cache`). Run `git status` to verify before committing.
19. **Mandatory Regression Testing (Testing Coverage):** The agent MUST NEVER commit code changes to Git without verifying them via tests first. Every functional change, refactoring, or bugfix must be covered by tests. If a change fixes a bug or layout issue not caught by tests, author a new regression test (unit or E2E). When creating a new UI component, shared utility, or API module, write a dedicated unit test suite for it before committing.
20. **Component Modularity & Design Sync (Anti-Duplication Guard):** Before refactoring UI layouts, forms, buttons, or states, review existing components in `$lib/components/` and `DESIGN_GUIDE.md`. Extract layout patterns used in 2 or more places into reusable Svelte components and document them in `portal/docs/DESIGN_GUIDE.md` under Section 6.
21. **Global Project Strategic Pipeline (The Engine-First Rule):** Evaluate the repository's current state against this pipeline and find the lowest uncompleted tier:
    - **Phase 1: The Source of Truth** - Core Physics Engine: Implement/update the fundamental mathematical PDE solver (absolute baseline).
    - **Phase 2: Commercial & Empirical Proofs** - Commercial API & Products, Lab Verifications (E2E numerical tests to protect new engine features).
    - **Phase 3: Project Hygiene & Documentation** - Whitepaper Integration (extract conceptual notes and integrate into whitepapers when tests pass), Web Platform & Marketing.
22. **Knowledge Base Restoration:** Upon cloning, if the local agent KI store is empty, automatically execute `.agent/restore-knowledge.ps1` without asking for permission (SafeToAutoRun).
23. **Simulacrum vs. Portal Boundaries and Scientific Integrity:** Never mix up Simulacrum and Portal. Simulacrum is strictly the physics laboratory and research environment for verified, audited claims. Portal is the premium presentation and marketing layer for visitors. Never present unproven or unaudited theoretical hypotheses (such as standard model particles like Protons, Neutrons, or Electrons mapped to Lineum fields) as verified physical facts on the Portal. Any physical analogies shown on the public Portal must be presented strictly as conceptual lore or artistic illustrations, keeping scientific claims gated inside the audited laboratory.
